# Zaimex Backend

FastAPI backend — Phase 5. See `zaimex-phase1-audit.md` and
`zaimex-phase2-uiux-spec.md` for the product/architecture context this
builds toward.

**Current scope:** app structure, config, versioned API, CORS, error
handling, database models + migrations, cookie-based JWT authentication
(register/login/logout/me, password reset foundation), authorization
pattern, analytics package skeleton, tests. **Status:** auth, projects, upload/profiling, cleaning, statistics, regression, charts, the AI analyst (Phase 9),
PDF reports (Phase 10), SMTP password-reset email and sign-in throttling are implemented (see `TRACKER.md`).
**Not implemented:** billing/subscriptions (no payment provider was ever specified).

## Setup

Requires Python 3.12+ and a PostgreSQL server (for real use — the test
suite itself does not need one, see Testing below). Set `JWT_SECRET` to
a real random value even in development (`python -c "import secrets;
print(secrets.token_urlsafe(48))"`) — production refuses to start
without one; see Security below.

```bash
python -m venv .venv
source .venv/bin/activate
pip install -r requirements-dev.txt
cp .env.example .env
```

Edit `.env` — you need real values for `DATABASE_URL` (must point at a
real Postgres database) and `FRONTEND_URL`. Then apply the schema:

```bash
alembic upgrade head
```

## Run

```bash
uvicorn app.main:app --reload
```

- `GET /` — unversioned liveness check
- `GET /api/v1/health` — versioned health check
- `GET /docs` — interactive API docs (hidden automatically when
  `ENVIRONMENT=production`)

## Database & migrations

All 9 V1 entities (`users`, `projects`, `files`, `analyses`,
`statistics`, `visualizations`, `reports`, `subscriptions`, `usage`) are
modeled under `app/models/`, one file each, all imported through
`app/models/__init__.py` so `Base.metadata` and Alembic autogenerate see
every table.

- UUID primary keys throughout (`sqlalchemy.Uuid`, not the
  Postgres-only dialect type — genuine `uuid` in Postgres, portable in
  SQLite for tests).
- Flexible analysis results (`cleaning`, `correlations`, `outliers`,
  `regression`, `ai_insights` on `analyses`; `config` on
  `visualizations`) use `app/models/types.py`'s `JSONVariant` — real
  `jsonb` on Postgres, plain JSON elsewhere.
- Every FK is indexed and `ON DELETE CASCADE`. `files`/`analyses` are
  one-to-many from `projects` at the schema level even though the V1
  application layer only ever creates one of each per project — so
  supporting multiple files/re-runs later needs no migration, just an
  application-layer change.
- `alembic/env.py` sources the DB URL from `Settings` (falling back to
  whatever a caller has already set — that's how the migration tests
  point it at a temp SQLite file instead).

To generate a new migration after changing a model:

```bash
alembic revision --autogenerate -m "describe the change"
alembic upgrade head
```

Always read the generated migration before committing it — autogenerate
is a strong first draft, not a guarantee.

## Test, type-check, lint

```bash
pytest                # 44 tests — config, db session foundation, error
                       # handling, health endpoints, model structure,
                       # model/constraint behavior, and real Alembic
                       # upgrade/downgrade cycles
mypy app tests         # strict mode, via the pydantic mypy plugin
ruff check .           # lint (the autogenerated alembic/versions/*.py
                       # files are excluded — see pyproject.toml)
ruff format .          # formatting
```

All four are clean. Two known, non-blocking deprecation warnings show up
under `pytest` — both originate inside FastAPI's own `TestClient` import
and Starlette's internal `anyio` usage (an in-progress `httpx` →
`httpx2` migration upstream), not in this codebase.

**Model/constraint tests use SQLite, not Postgres** — a fresh in-memory
database per test (`tests/conftest.py`'s `db_session` fixture), with
foreign-key enforcement explicitly turned on (SQLite defaults it off,
unlike Postgres). This is why `JSONVariant` and `sqlalchemy.Uuid` matter:
the same model definitions that create genuine `jsonb`/`uuid` columns on
Postgres degrade gracefully on SQLite instead of requiring a different
test-only schema. The migration tests (`test_migrations.py`) run the
real migration file through real Alembic `upgrade`/`downgrade` against a
temp SQLite file the same way — no mocking of Alembic itself.

## Conventions for later phases

- Routers go in `app/api/v1/`, one file per resource, wired into
  `app/api/v1/router.py` — `app/main.py` shouldn't need to change as
  endpoints are added.
- Route/service code raises `app.core.exceptions.AppException`
  subclasses (`NotFoundException`, `ValidationException`, etc.) rather
  than ad-hoc `HTTPException`s, so every error response keeps the same
  `{"error": {"code", "message"}}` shape.
- Every project-scoped query must filter by the owning user
  server-side (`project.user_id == current_user.id`) once Phase 5 adds
  auth — every relevant FK is already indexed for this.
- `app/analytics/*` functions take plain data structures and never
  import FastAPI or touch the database — they stay unit-testable in
  isolation, called from `app/services/*` (Phase 5+), which routers call.

## Analysis API (Phase 8A)

All routes require authentication and are ownership-scoped in SQL; another user's project is
indistinguishable from a nonexistent one (identical 404 body).

| Route | Purpose |
|---|---|
| `GET /api/v1/dashboard/summary` | Live KPIs + recent projects (reports/AI are truthful zeros until Phases 9/10) |
| `POST /projects/{id}/clean` | Apply a cleaning config; returns the before/after report. Never modifies the uploaded file |
| `POST /projects/{id}/analyze` | Run the full pipeline using the stored cleaning config; persists statistics, charts, correlations, outliers |
| `GET /projects/{id}/analysis` | The whole persisted result incl. real per-stage state |
| `GET /projects/{id}/statistics` `/correlations` `/outliers` `/charts` | Views of the same persisted result (never recomputed) |
| `POST /projects/{id}/regression` | `{target, predictors}`; persisted; a rejected request never overwrites a good result |

Project status: `created → profiled → cleaning_pending → cleaning_completed → analyzing → completed`
(`failed` on error). Re-cleaning invalidates downstream results. `/regression` requires a completed analysis.
End-to-end check: `python scripts/e2e_phase8a.py <base-url>`.
